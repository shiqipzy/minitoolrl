# MiniToolRL 术语表

这份表配合[项目说明](项目说明.md)、[训练与评测](训练与评测.md)和 [DeepSpeed 与 vLLM 入门](DeepSpeed与vLLM入门.md)阅读。

| 术语 | 本项目中的含义 |
|---|---|
| 世界 `world` | 一套后台初始数据，包括客户、订单、商品库存和运单；每次任务执行复制独立快照 |
| 任务 `TaskInstance` | 初始世界、用户需求、参考调用与评分断言的组合 |
| 任务族 `family` | 一类业务流程，例如退款回库或按等级补偿 |
| 工具调用 `call` | 执行一次读取或修改后台状态的函数 |
| 退款单 `refunds` | 执行退款后保存的记录，包含退款编号、订单号、金额和原因；当前每个订单最多要求一张 |
| 工单 `tickets` | 通过 `open_ticket` 创建的处理事项，包含类别、关联订单或商品、说明和状态 |
| 操作日志 `mutations` | 后台自动记录写工具执行了什么、作用于哪个对象，供统计和排查使用 |
| 观察 `observation` | 一次工具调用返回给模型的信息或错误 |
| 轮 `turn` | 模型一次生成 assistant 文本，可包含一个或多个工具调用 |
| 回合 `episode` | 从初始状态开始处理一个任务的一次完整尝试 |
| 轨迹 `rollout` | 该次尝试中的消息、调用、工具返回与最终结果 |
| 参考调用 `gold_calls` | 用于生成 SFT 训练轨迹和验证任务可执行的一条正确操作计划 |
| 断言 `assertion` | 一项可执行评分条件，如退款金额、库存增量或其他订单未改动 |
| 完整成功 `success` | 最终状态满足全部断言；模型声称完成不计为成功 |
| SFT | 按训练轨迹上下文学习应生成的工具调用和答复 |
| 监督 token | 真正进入 SFT 损失的 assistant 输出位置 |
| `policy_mask` | 指定参与训练的模型输出位置；工具观测与用户输入不计入监督目标 |
| teacher forcing | 预测参考 token 时使用前面的参考 token；不等同模型自主执行 |
| GRPO | 同一任务采样多条学生轨迹，以组内奖励差异更新模型 |
| G0 | GRPO 完成后的检查点，三个 SFT 续训分支的共同起点 |
| on-policy | 轨迹由当前学生策略自主采样生成 |
| 二值奖励 | 全部状态断言通过为 1，否则为 0 |
| 零信号组 | 同组奖励没有差异，无法提供组内优势信号 |
| 回放 `replay` | 在追加 SFT 中继续使用基础任务训练轨迹 |
| 分解任务 | 将组合业务需求拆成分别训练的任务；当前 C 数据使用信用补偿工单、部分退款通知，每轮共 576 条轨迹 |
| C 训练数据 | 分解任务轨迹与基础任务回放，共 1,152 条记录 |
| U 训练数据 | 六类基础任务均衡训练轨迹，共 1,296 条记录 |
| `C_blocked` | 每轮先使用回放记录，再使用分解任务记录 |
| `C_mixed` | 与 C_blocked 相同的记录，使用固定混排日程 |
| `U_mixed` | 原任务均衡数据的固定混排，提供接近的监督 token 预算 |
| K / R / T / N | 信用补偿 / 部分退款与改状态 / 工单 / 通知 |
| capped / uncapped | 补偿金额达到 / 未达到客户等级对应上限 |
| 组合留出 | 训练见过所需工具，但没有见过评测要求的完整操作组合 |
| A/B 表达 | 同一世界和任务目标的两种指令表达，统计时按世界配对 |
| greedy | 每步选概率最高的 token，完整自主执行一次任务 |
| 配对 bootstrap | 重采样相同世界，计算模型之间的成绩差值区间 |
| DDP | PyTorch 的分布式数据并行封装，各进程处理数据并同步梯度；本项目生产训练使用 DeepSpeed ZeRO-2 |
| DeepSpeed ZeRO-2 | 生产训练后端：分片优化器状态和梯度，模型参数每卡保留完整副本；bf16 计算、fp32 优化器主权重、不 offload |
| 一次全局更新 | 训练后端对外的最小单位：一个更新组的全部 microbatch 只做一次梯度裁剪和一次优化器步 |
| 零损失补齐 | rank 上真实 microbatch 少于累积步数时，用零损失反向对齐累积边界；不复制真实样本、不产生梯度 |
| 训推分离 | 训练进程与采样进程分开部署：训练卡跑 DeepSpeed，采样卡常驻 vLLM 进程 |
| 权重同步 | 每次有效更新后把新参数传给 vLLM：传输参数 → 清除旧前缀缓存 → 确认版本号 → 接受下一批请求；失败即结束本阶段 |
| `policy_version` | 策略版本号；每完成一次有效更新加一，采样批次必须与训练侧版本一致 |
| Prefill | 成批处理已知提示，建立 KV 缓存，产生预测首个输出 token 所需的结果；可复用命中的前缀 |
| Decode | 逐步生成阶段；常规自回归每步处理刚生成的 token、读取历史 KV，预测下一个 token |
| KV cache | 各层已计算的 K、V；避免重算历史 token 的前向，新 query 仍需读取历史 KV |
| 前缀缓存 | 新请求复用相同前缀已算出的 KV；本项目更新权重后清除旧缓存 |
| 连续批处理 | 按生成进度调整批次成员，让等待请求在资源允许时加入；项目的工具轮仍等待本次生成全部返回 |
| 分块 prefill | 按调度预算把长提示分多次处理，与已有 decode 协调；不等于减少提示本身的计算量 |
| PagedAttention | 将 KV 分块管理，并让注意力通过块表访问缓存；减少预留与碎片，不是压缩 KV 数值 |
| FlashAttention | 减少注意力显存读写与中间存储的算法及实现；vLLM 可以采用，其他框架也可采用 |
| FA2 / FA3 | FlashAttention-2 / FlashAttention-3，不同代的实现；不能由 `sdpa` 配置推断实际代际 |
| SDPA | 缩放点积注意力；项目的 `attn_implementation='sdpa'` 指训练模型使用 PyTorch SDPA 接口，底层可选择 FlashAttention 等内核 |
| CUDA Graph | 捕获并重放 GPU 操作与依赖，减少重复提交开销；每次重放仍计算新的结果 |
| TTFT / ITL | 首 token 延迟（含排队）/ 相邻输出 token 的时间间隔；当前整体生成耗时不能直接给出这两项指标 |
| 全局 batch | 一次优化器更新涉及的全部进程记录总量 |
| 强扩展 | 固定全局工作量，比较增加卡数后的速度；本项目 SFT 成对短测采用此设置 |
| 成对短测 | 同起点、同预定长度、明确控制条件的一组测量；不作为主链训练终点 |
| GPU 秒 | 墙钟秒数 × 实际占用卡数；同一批测量同时给出两个口径 |
| 固定预算终点 | 完成预定更新或迭代后选定的模型，不按终测成绩挑选 |
| 梯度累积 | 多个小批次累计梯度后进行一次优化器更新 |
| 检查点 `checkpoint` | 保存的模型、tokenizer、模板及相应状态 |
| `pins.json` | 运行器记录的检查点路径、哈希与训练阶段身份 |
| `budget.json` | 实际执行阶段的时间记录，用于核对训练开销 |

记录数不一定等于独立任务数；A/B 表达、回放和重复曝光会使同一任务出现多次。验证时必须区分输入 token、监督 token、采样迭代和优化器更新。
