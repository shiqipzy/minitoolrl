# MiniToolRL 项目说明

MiniToolRL 是一个轻量的多轮工具调用训练项目。它在可执行的电商业务环境中训练 Qwen3-0.6B，研究训练轨迹的内容与组织方式怎样影响模型在未见技能组合上的任务完成率。

输入格式版本为 `all-restock-v1-20261011`，默认新运行标识为 `tool_composition_qwen3_registry_lr2e6`。训练输入已构建并通过程序校验，工具列表统一使用 registry 顺序；该新运行尚未执行 GPU 训练。

## 研究问题

模型在训练中分别接触退款、回补库存、取消运单、释放预留、发放信用、开工单与通知客户。评测要求它把已见操作组合起来完成新需求。

项目先建立共同的 SFT 与 GRPO 起点 `G0`，再比较三组监督续训：

- `C_blocked`：原任务回放与分解任务轨迹按文件中的分块顺序训练。
- `C_mixed`：使用同一份 C 训练轨迹，按固定更新日程混排原任务回放与分解任务轨迹。
- `U_mixed`：继续训练原有六类任务，按任务族混排，并匹配更新数与监督 token 预算。

`C_mixed` 与 `C_blocked` 的对照检验数据组织方式；`C_mixed` 与 `U_mixed` 的对照检验分解任务轨迹相对于原任务续训的效果。实验结果用于判断这些具体设置下的表现，不预设哪一组一定更好。详细日程见[训练与评测](训练与评测.md)。

共同起点由一段连续 SFT 和一次 GRPO 建立；SFT 终点与 G0 都参加相同评测，直接观察奖励训练前后的变化。项目也包含工程验证：SFT 与三组续训走 DeepSpeed ZeRO-2 分布式训练，GRPO 把训练卡与 vLLM 采样卡分开部署并在每次有效更新后同步权重；工程阶段核对同一次更新在 1 个和 2 个 rank 下的损失、梯度与参数，比较单/双 rank 的 SFT 吞吐、显存与数值漂移，核对 DeepSpeed/vLLM 采样、更新和权重同步并记录实际吞吐。这些与实验对照共同构成项目的能力证据。

## 可执行环境

每条任务有独立的初始世界快照，包含客户、订单、库存、运单，以及退款单、信用补偿、工单与通知记录。金额用整数分表示。模型通过工具读取信息或修改状态，每次调用返回实际执行结果；工具参数或业务条件不合法时返回错误信息。

环境提供 13 个工具：5 个查询工具 `get_order`、`get_customer`、`get_inventory`、`get_policy`、`search_orders`，以及 8 个写入工具 `create_refund`、`restock_item`、`release_reservation`、`update_order_status`、`cancel_shipment`、`apply_credit`、`open_ticket`、`notify_customer`。同一工具集合向模型公开，避免按题目裁剪工具列表而泄漏操作计划。

工具的职责分开定义：退款不会自动回补库存或修改订单状态；取消运单不会自动释放预留；发放信用不会自动开工单。模型需要按需求完成各个必要操作。

执行 `create_refund` 后，后台增加订单的已退款金额，并生成一张退款单（`refunds`），记录退款编号、订单号、金额和原因。工单（`tickets`）记录题目要求的处理事项，通过 `open_ticket` 单独创建。后台还会自动保存操作日志（`mutations`），用于统计和排查。

当前每个订单最多要求退款一次。双订单批量退款生成两张退款单，分别对应两个订单；不设置同一订单连续退款两次的任务。信用补偿、工单和通知分别最多要求一条记录。

业务规则包括：

- 全额退货回库任务处理订单中全部 `restockable=true` 的商品，逐一按订单数量回补。不可回补商品的库存保持不变。
- 部分退货任务只回补题目指定的 SKU 与数量。商品不退回的退款任务不改变库存。
- 信用补偿与退款可以分别执行，是否同时执行以题目要求为准。
- 只在题目要求时创建相应类别的工单、发送相应模板的通知。
- 订单最终状态按任务确定：普通全额退款为 `refunded`，部分退款为 `partially_refunded`，取消退款为 `cancelled`。
- 等级补偿为 `min(total_cents × percent // 100, cap)`：regular 为 2%/2000 分上限，silver 为 5%/5000 分，gold 为 10%/10000 分。

任务定义见 [tasks.py](../env/tasks.py)，工具执行见 [tools.py](../env/tools.py)，政策入口见 [policy.py](../env/policy.py)。

## 六类基础任务与三类组合任务

| 基础任务                  | 需要完成的操作                                         |
| ------------------------- | ------------------------------------------------------ |
| `refund_restock`        | 全额退款、全部可回补商品回库、更新为 refunded          |
| `cancel_unshipped`      | 取消未发货订单的运单、更新为 cancelled                 |
| `partial_refund_notify` | 按指定商品数量计算部分退款、更新状态、通知客户；不回库 |
| `tier_compensation`     | 查询订单、客户等级与政策、计算并发放信用、开补偿工单   |
| `inventory_correction`  | 读取库存、按盘点差额增减库存、开库存工单               |
| `stuck_reservation`     | 释放已取消订单中指定商品的预留、开库存工单             |

| 留出组合任务                      | 需要组合的操作                                             |
| --------------------------------- | ---------------------------------------------------------- |
| `refund_with_credit`            | 全额退款＋等级信用补偿＋更新订单状态；不回库、不额外开工单 |
| `partial_refund_restock_ticket` | 部分退款＋指定数量回库＋退款工单＋更新状态                 |
| `cancel_refund_release`         | 取消运单＋全额退款＋释放指定预留＋更新为 cancelled         |

组合任务使用的工具已在基础任务中出现，训练轨迹不包含以上目标写操作组合。除按任务族检查外，输入校验还检查参考调用、结构化需求和参与损失的调用，拒绝目标组合进入 SFT 训练轨迹。定义见 [decomposition_tasks.py](../data/decomposition_tasks.py) 与 [composition_suite.py](../data/composition_suite.py)。

## 成功判定

评分器检查模型执行后的世界状态，而不是最终回复是否声称完成任务。期望的退款单、信用补偿、工单和通知记录，需要逐条匹配到最终实际生成的记录：数量相同，指定字段相同，记录顺序可以不同。例如双订单批量退款分别按订单号核对两张退款单的金额。订单状态、金额、库存、预留和运单按精确值检查；非目标实体的状态须保持不变。全部断言通过时成功值为 1，否则为 0。单条断言通过率只用于诊断，不作为 GRPO 奖励。

参考调用用于构造 SFT 训练轨迹和检查任务可执行性。模型评测依靠实际工具执行与最终状态评分，不要求生成与参考调用完全相同的文字或操作顺序。评分实现见 [grader.py](../env/grader.py)。

## 一条实际训练记录

这条记录来自当前输入包 `data/sft_train_v2.jsonl` 第 751 行，任务 ID 为 `cancel_unshipped#100000`。

> 订单 O-2218 尚未发货，客户临时不要了。请取消它的运单，再把订单状态置为 cancelled。

| 轮次 | 模型应生成的调用                                                       | 工具真实返回摘要                     |
| ---- | ---------------------------------------------------------------------- | ------------------------------------ |
| 1    | `get_order({"order_id": "O-2218"})`                                  | status=paid, shipment_status=pending |
| 2    | `cancel_shipment({"order_id": "O-2218"})`                            | shipment_status=cancelled            |
| 3    | `update_order_status({"order_id": "O-2218", "status": "cancelled"})` | status=cancelled                     |

最后回复：已完成上述操作。

这里取消运单和修改订单状态是两次不同的写操作。任务不要求退款或回库；评分还会检查未要求的退款单、信用补偿、工单、通知以及其他订单和库存没有被改动。

SFT 读取 `prompt`、`turns` 和 `final_line`；系统规则与工具定义来自当前环境代码。记录中的 `world`、`assertions` 和参考调用保留用于复查任务，不直接拼进模型提示。每次返回是工具实际执行的结果。

使用固定版本官方 Qwen3 tokenizer 时，这条记录共 **1688 个输入 token、91 个监督 token**。只有正确的工具调用、最后回复及其 EOS 参与损失；系统规则、题面、工具说明、工具返回与预填的 assistant 开头均不参与损失。

下面是第一轮模型需要生成的正文（EOS 单独显示为 `<|im_end|>`），由官方模板直接渲染：

```text
<tool_call>
{"name": "get_order", "arguments": {"order_id": "O-2218"}}
</tool_call><|im_end|>
```

官方非思考模式会预填 `<think>\n\n</think>\n\n`。这是 Qwen3 官方模板的输出；程序使用 `enable_thinking=False`，不自行改写模板。模型采样以 EOS 结束，工具返回与下一轮开头追加为上下文。

原始 JSONL 为机器读取格式，阅读任务时先看这里的题面、调用和返回关系；不需要打开整份 token 数组。

已准备的训练输入在 `minitoolrl/artifacts/inputs/`。基础 SFT 使用六类基础任务的参考轨迹，C 两组追加分解任务与基础任务回放，U 组继续使用六类基础任务；GRPO 的调用轨迹由模型在训练时生成。具体数据量和训练方式见[训练与评测](训练与评测.md)，输入包准备与启动核对见[运行指南](运行指南.md)。

- 环境：`minitoolrl/env/`

- 训练后端与采样后端：`minitoolrl/train/deepspeed_backend.py`、`minitoolrl/train/vllm_backend.py`
- 评测与分析：`minitoolrl/eval/`
- 配置与对照：[训练与评测](训练与评测.md)
- 环境准备、逐阶段执行与输出：[运行指南](运行指南.md)
